# Сборка интерфейса по DESIGN.md

## Зачем скилл существует

Генерация дизайна деградирует от прогона к прогону, потому что у неё нет
обязательного входа: каждый раз заново выбираются палитра и шрифты. Проверено на
этом проекте дважды — оба раза модель уходила в свою сторону, пока не появился
файл.

Хук кладёт выжимку из `DESIGN.md` в контекст перед записью, но хук не умеет
судить, *правильно* ли применена система, и не умеет спрашивать человека. Это
работа скилла.

## Железное правило

```
DESIGN.md → npm run design:tokens → код
```

Никогда наоборот. **Из этого скилла `DESIGN.md` не правится.** Если по ходу
работы кажется, что файл неверен — остановиться и сказать об этом человеку.
Правка файла — отдельное решение и отдельная сессия, потому что она тянет за
собой переписывание экранов.

## Процедура — пять шагов, каждый со статусом

Статус печатается **после** шага, коротко, и содержит факт, а не намерение.

### Шаг 1. Прочитать DESIGN.md целиком

Выжимка из хука — напоминание, а не источник. Источник — сам файл, и читается
он полностью, включая прозу: разделы `Elevation & Depth`, `Content`, `Presence`
и `Affordance` не выражены токенами вовсе, а нарушаются чаще всего.

```
▶ 1/5  DESIGN.md прочитан
       токены: N цветов · N ступеней типографики · N радиусов
       правила прозой, применимые к задаче: [перечислить те, что реально касаются экрана]
```

### Шаг 2. Назвать компоненты системы до написания кода

Какими компонентами из раздела `Components` собирается экран. Если нужного
компонента в системе нет — **это не повод изобрести его на месте**: сказать
человеку, что система не покрывает случай.

```
▶ 2/5  План
       задействую: panel · option-card · button-filled · input · hint-text
       новых сущностей не завожу
```

### Шаг 3. Написать код

Только имена токенов. Ни одного литерала цвета, шрифта, радиуса.

Исключение помечается `design-ok: <причина>` на строке или над ней. Причина
обязательна. **Больше двух-трёх исключений на экран — останавливаться:** это
сигнал, что неправ файл, а не код.

```
▶ 3/5  Записано
       src/pages/public/RequestForm.tsx · src/texts/request.ts
       исключений design-ok: 0
```

### Шаг 4. Четыре проверки, с реальным выводом

```bash
npm run design:check    # код против файла: литералы и запрещённые утилиты
npm run design:lint     # сам файл: ссылки, контраст, порядок разделов
npx tsc -b --force      # типы
npx oxlint              # линтер
```

Вывод приводить как есть. Пересказ вывода вместо вывода — то же самое, что его
отсутствие.

```
▶ 4/5  Проверки
       design:check — чисто
       design:lint  — 0 errors, 0 warnings
       tsc exit 0 · oxlint чисто
```

### Шаг 5. Посмотреть глазами и остановиться

Проверки не видят смысла. Обязателен проход браузером на **375px** и на широкой
ширине, со скриншотом.

Своими глазами проверить то, что машина не ловит:

- одна главная кнопка на экран
- плашка стоит там, где есть смысл «это одно целое», а не вокруг самостоятельного элемента
- вложенность поверхностей не глубже второго уровня
- вложенные радиусы концентричны
- надпись у действия говорит о действии
- текст не ведёт за ручку и не пересказывает то, чему место в FAQ
- пустые состояния говорят словами
- падежи согласованы

```
▶ 5/5  Браузер, 375px и широкий
       [скриншот]
       смысловая проверка: [что сошлось, что нет]

СТОП. Расхождений нет → идём дальше или правим?
```

## Шлюз и пределы цикла

**После пятого шага — остановка и вопрос человеку. Всегда.** Даже когда всё
зелёное: зелёные проверки не означают, что экран получился.

При расхождении:

1. Назвать расхождение: файл, строка, какое правило `DESIGN.md` нарушено
2. Починить
3. Перепроверить

**Два предела, оба жёсткие:**

- **Не больше двух автоматических попыток** на одно расхождение. После второй —
  стоп и вопрос, независимо от того, насколько близко кажется решение.
- **То же расхождение всплыло дважды → немедленный стоп**, без второй попытки.
  Повтор означает, что причина не понята, и третий заход её не найдёт.

Остановка — нормальный исход, а не провал. Бесконечный цикл правок дороже
одного вопроса человеку.

## Чего этот скилл не делает

- **Не правит `DESIGN.md`** — см. железное правило
- **Не запускает субагентов** — сборка экрана идёт в главном цикле; делегирование
  ломает единственное, ради чего скилл существует: что файл прочитан тем, кто пишет
- **Не трогает `src/contract` и `src/api`** — это ядро и стык, у них своя дисциплина
- **Не пишет тексты в разметку** — тексты живут в `src/texts` и `src/questions`
- **Не добавляет DOM-тесты** — решение PM: тестами покрыты контракт, моки,
  http-клиент и разбор телефона, экраны не покрываются

## Связь с остальным

- Хук `PreToolUse` кладёт выжимку (`scripts/design-brief.mjs`) перед записью
- Хук `PostToolUse` гоняет `design:check` сразу после записи
- `/review` вызывается **после** этого скилла, когда экран принят человеком
- `hallmark audit` — по желанию, берём только `audit`
