# lidgen

## Что за проект
Эксперимент Asia Mebel: проверяем, можно ли приводить заказчиков мебели на заказ
и сводить их с отобранными мебельщиками. Монетизации нет.
**Статус:** документы готовы, кода нет. Следующий шаг — срез 1 «Скелет»,
10 историй, состав в `docs/story-map.md`. Точка входа — `docs/HANDOVER.md`.

## Стек

Выбран 15.09.2026, **уточнён решением разработчика в тот же день:
фронт на React, API мокается.** Бэкенд и модель данных делает разработчик —
PM их не пишет.

### Зона PM — то, что строится вайбкодом

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **TypeScript** | типы контракта общие с будущим бэком |
| Библиотека | **React** | решение разработчика |
| Сборка | **Vite** | 🔵 если разработчик сводит всё в Next — сказать до старта |
| Стили | **Tailwind CSS** | быстро, без своей дизайн-системы с нуля |
| Валидация и контракт | **zod** | одна схема описывает и поля формы, и ответы API; ею же валидируются моки |
| Маршрутизация | **React Router** | десять экранов, три зоны доступа |
| API | **моки по контракту** | не «как удобно фронту»: моки реализуют тот же контракт, что потом реализует бэк |

### Зона разработчика — PM не трогает

PostgreSQL · схема и миграции · авторизация двух ролей · маршрутизация заявки ·
отправка OTP · Telegram-уведомления · хранение ПДн · хостинг.

⚠️ **Хостинг и закон о персональных данных РК.** Собираются телефоны граждан
Казахстана. Требование локализации ПДн может запрещать хранение за пределами РК.
Вопрос переходит в зону разработчика, но **владелец решения — PM**, до GATE 1.
На фронте с моками реальных ПДн нет — риск появляется в момент стыковки.

**Чего в стеке нет:** Next.js на этом этапе (бэка у фронта не будет) · Redux
и прочих стор-менеджеров (состояние локальное, десять экранов) · Docker ·
внешней аналитики — события уходят через тот же контракт.

## Дизайн-система — DESIGN.md

**Единственный источник правды по визуалу — `DESIGN.md` в корне.** Формат —
спецификация Google Labs (Apache-2.0), локальная копия в
`docs/reference/design-md-spec.md`, линтер `@google/design.md` в devDependencies.

Причина такого устройства: генерация дизайна деградирует от итерации к итерации,
потому что у неё нет обязательного входа. Каждый прогон заново выбирает палитру
и шрифты. Файл лечит это, только если его читают принудительно.

- **Перед любой генерацией или правкой UI — сначала прочитать `DESIGN.md`.**
  Не «если вспомнишь», а первым действием. Нет файла — не генерировать интерфейс,
  а сказать об этом.
- **Правки идут через файл, код следом.** Поменять цвет в компоненте, не тронув
  `DESIGN.md`, — значит развести их. Порядок: файл → `npm run design:tokens` →
  код. Не наоборот.
- **Проверка после генерации, три контура:**
  `npm run design:lint` — схема, ссылки токенов, контраст WCAG ·
  греп на цвета и шрифты вне токенов — следовал ли код файлу ·
  `hallmark audit` — анти-паттерны. От hallmark берём **только** `audit`:
  его собственный выбор темы и правило разнообразия под эту схему вредны,
  они специально уводят каждую следующую страницу в сторону.
- **`npx design.md diff before.md after.md`** — что именно изменилось в системе.
  Прогонять перед тем, как принять правку файла.
- **`design:check` ловит два класса нарушений.** Литералы — `#ff0000`,
  `oklch(...)`, `font-family` строкой. И **запрещённые утилиты Tailwind** —
  `rounded-*`, `font-bold`, `shadow-*`, `italic`, лайм заливкой. Второе нужно
  потому, что Tailwind v4 свои дефолты нашими токенами не заменяет,
  а дополняет: объявленный единственный радиус `none` не отменяет `rounded-xl`.
- **Исключение помечается в коде:** комментарий `design-ok: <причина>` на строке
  или над ней. Причина обязательна — молчаливых исключений не бывает.
  Если исключений становится больше двух-трёх, это сигнал, что неправ файл,
  а не код: правим `DESIGN.md`.
- **Чего никакая проверка не удержит:** «не набирать капсом связный текст»,
  «выравнивание левое», «не показывать названия материалов». Эти правила живут
  прозой и держатся только на том, что `DESIGN.md` прочитан первым.
- **Токены в код не переписывать руками** — `npm run design:tokens` отдаёт
  Tailwind v4 `@theme` из файла. Есть ещё `dtcg`, `css-vars`, `json-tailwind`.
- Спеку обновлять только командой `npm run design:spec`, руками не трогать.

## Структура

```
src/
  pages/
    public/     лендинг, каталог, карточка мастерской, форма заявки
    client/     страница КП по токену — вход без регистрации
    master/     кабинет мебельщика — вход по номеру и коду
  components/   переиспользуемое представление
  contract/     ЯДРО СТЫКА: zod-схемы запросов и ответов, типы
  api/
    client.ts   единая точка вызова — переключается мок ↔ реальный бэк
    mocks/      реализация контракта в памяти
  questions/    ЯДРО: тексты и наборы вопросов формы, самое ценное в пробе
  texts/        пользовательские тексты интерфейса, русский
docs/           канвас, спека, план, PRD, персоны, карта историй, контракт API
```

**Два места, которые переживают эксперимент** (спека §1.3, зона PM):
`src/questions` — формулировки вопросов и наборы вариантов ·
`src/contract` — описание того, чем обмениваются стороны.
Всё остальное на фронте — оболочка.

## Конвенции

- **Оболочка помечается в коде:** `// PROBE: <что и почему>` над каждым куском,
  который удаляется после GATE 2 — тестовый OTP `1234`, демо-данные, ручные обходы.
  На утилизации ищется через `grep -rn "PROBE:"`, а не по памяти.
- **Моки реализуют контракт, а не обходят его.** Любой мок возвращает то, что
  описано в `src/contract` — включая ошибки и пустые состояния. Мок, отвечающий
  «как удобно экрану», — главный источник потерянной недели на стыковке.
- **Через `api/client.ts` и только через него.** Ни один компонент не ходит
  в моки напрямую: подмена на реальный бэк должна быть переключателем,
  а не переписыванием экранов.
- **Контракт меняется первым.** Понадобилось новое поле — сначала правится
  `src/contract` и документ контракта, потом мок, потом экран.
- **Коммит ссылается на историю:** `US-19a: форма КП с обязательной вилкой`.
  Истории — `docs/prd-lidgen.md` §7, порядок работ — `docs/story-map.md`.
- **Никаких персональных данных в localStorage** — спека §8, US-11.
  На моках соблазн сложить заявку в браузер особенно велик: нельзя.
- **Язык интерфейса — русский**, тексты в `src/texts`, не разбросаны
  по компонентам: их правят по итогам дозвонов.
- **Сначала срез 1, потом срез 2** — состав в `docs/story-map.md`. Соблазн
  сделать красиво один экран вместо сквозного прохода — главная ловушка пробы.

## Среда
- PM-скиллы: 77 штук лежат файлами в `.claude/skills/<имя>/SKILL.md`.
  Источник — deanpeters/Product-Manager-Skills v0.84 (`1b5a524`),
  лицензия CC BY-NC-SA 4.0. Подключены только в lidgen.
  **В git не хранятся** — см. `.gitignore`: это инструмент разработки,
  а не часть продукта, плюс NC-лицензия.
- Установка и обновление скиллов (на новой машине, после клона репозитория):
  `claude plugin marketplace add deanpeters/Product-Manager-Skills`
  затем `cp -R ~/.claude/plugins/marketplaces/pm-skills/skills/. .claude/skills/`
  Маркетплейс регистрируется глобально, в настройках проекта его не закрепить —
  ключ `extraKnownMarketplaces` работает только в managed settings.
  Локальные правки скиллов при обновлении перезапишутся.
- Почему файлами, а не плагинами: desktop-клиент не поднимает плагины,
  включённые через `enabledPlugins` в настройках проекта (проверено —
  `claude plugin list` их видит, приложение нет). Файлы в `.claude/`
  читаются нормально, как и команды.
- Типы скиллов: Workflow (20) → Interactive (29) → Component (28).
  Не знаешь инструмент → Interactive (`*-advisor`); знаешь этап → Workflow;
  знаешь артефакт → Component.
- Слэш-команды: `.claude/commands/` — /discover, /strategy, /write-prd,
  /plan-roadmap, /prioritize, /leadership-transition. Каждая тянет связку скиллов.

## Работа со скиллами
- Перед вызовом скилла — назвать его явно, до вызова:
  `→ Вызываю problem-framing-canvas — уточнить формулировку проблемы перед решениями`
- Отвечаю без скилла — сказать прямо: `→ Без скилла`
- Подходит несколько — назвать выбранный и альтернативы одной строкой:
  `→ Вызываю prioritization-advisor (альтернативы: feature-investment-advisor, recommendation-canvas)`
- После отработки — `← problem-framing-canvas отработал`
- Если скилл предложен, но не запущен — не начинать работу руками молча,
  дождаться «да» или «пропускаем»
- Перед вызовом скилла — карточка:
  **Что это** — тип скилла и что он делает
  **Зачем сейчас** — какую дыру закрывает в текущей работе
  **Результат** — что получим и куда ляжет
  **Объём** — сколько вопросов, сколько времени
- Вместе с карточкой — пайплайн текущего процесса с отметкой позиции:
  `✔` пройдено · `▶` сейчас · пусто — впереди · `─` пропущено, с причиной
- Пайплайн показывать и при завершении шага, чтобы был виден сдвиг

### Цепочки и фасилитатор
- **Скилл-цепочка идёт целиком.** Если команда или скилл перечисляет связку
  (`/write-prd` = problem-statement → proto-persona → prd-development →
  user-story → user-story-splitting), проходятся **все звенья по порядку**,
  каждое со своей карточкой и своим апрувом. Одно «да» = одно звено,
  на цепочку оно не распространяется.
- **У каждого скилла свой формат выхода.** Артефакт кладётся туда, куда
  предписывает скилл (`proto-persona` → `docs/proto-personas.md`), а не вливается
  в чужой документ. Вливание — только по отдельному решению пользователя.
- **Фасилитатор подключается автоматически.** Перед запуском скилла с
  `type: workflow` или `type: interactive`, который ссылается на
  `workshop-facilitation`, открывать сессию его протоколом: вводная
  со временем и числом вопросов → выбор режима (Guided / Context dump /
  Best guess) → **один вопрос за ход** → метка прогресса `Qx/N` →
  нумерованные варианты с `Свой вариант` → рекомендации только в точках
  решения → финальная сводка.
  **Проверять по файлу скилла**, а не по памяти: `grep -l workshop-facilitation`.
  Component-скиллы его не берут — им хватает чек-листа.
- Несколько вопросов одним блоком — нарушение протокола, а не экономия времени.
