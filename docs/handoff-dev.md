## 1. Что уже сделано и чего касаться не нужно

## 3. Что реализовать в срезе 1

Двадцать операций: десять публичных (§5), четыре — вход и кабинет
заказчика (§5в), шесть — кабинет мебельщика (§5б). Полный список
с методами, телами и кодами ошибок — `docs/api-contract.md`.

Порядок, в котором их удобно поднимать:

1. `createRequest` → `confirmOtp` → `getRequestByToken` — без них не живёт ничего.
2. `authRequestCode` → `authConfirmCode` → `listRequestsForMaster` — вход
   и кабинет. Дверь одна на обе роли: `authConfirmCode` отдаёт
   `Session {token, roles, expiresAt, master}`, кабинет заказчика
   (`listMyRequests`) поднимается той же парой без дополнительной работы.
3. `createQuote` → страница предложений. На этом сквозной путь замкнут.
4. Остальное: фотографии, каталог, карточка мебельщика, события.

**Пять правил, которые ломаются легче прочего:**

- **Проекции строгие.** Лишнее поле роняет разбор, а не проглатывается: так
  утечка телефона в список становится ошибкой стыковки, а не находкой на проде.
- **Телефон мастерской не уходит в публичные операции.** `listMasters`
  и `getMasterCard` открыты без токена; контакт вырезан схемой
  (`PublicMasterCard`), а не скрыт на экране.
- **Заявка без размера — законная заявка.** «Не знаю» принимается и уходит
  мебельщикам как есть (решение PM 18.09).
- **У материалов КП две подписи на одно значение** (§2, 21.09): цеховая
  для мебельщика, простая для заказчицы. Значение одно — сравнение
  не рассыпается. Подписи живут в `src/questions/composition.ts`, контракт
  знает только идентификаторы.
- **Роль проверяется при каждом вызове кабинета, а не берётся снимком
  из сессии**, и дверь отвечает одинаково любому номеру. Оба требования
  ломаются первыми, потому что «положить роль в токен и верить ему» —
  естественный ход. Цена: мастерская, снятая с публикации, сохранит доступ
  до конца двенадцати часов, а дверь, отвечающая «такого мебельщика нет»
  до ввода кода, перечисляет реестр по номеру. Подробности — §5в.

Три ломающих правки контракта. Если вы начали читать раньше этого дня —
перечитайте §2.

| Что | Где |
|---|---|

Рассрочки среди признаков карточки нет намеренно: она уже живёт услугой
`installments` с условием, и второй источник правды о ней завести нельзя.

## 5. Чего в контракте намеренно нет

- **Цен в карточке мастерской** — ни в каком виде (PRD US-02).
- **Переназначения заявки** — маршрут пишется один раз.
- **Модерации карточек** — решение 18.09: снимки грузит мебельщик,
  модерации в пробе нет. На проде она встаёт сюда, место под неё в статусах
  карточки есть.
- **Регистрации мебельщика** — карточки заводим мы (трек A2).
- **Рейтингов и отзывов** — им неоткуда взяться до первых сделок.

## 6. Как запустить и проверить фронт

```bash
npm install
npm run dev          # экраны на моках
npm test             # 356 тестов: контракт, моки, http-клиент, форматирование
npm run e2e          # 9 сквозных сценариев
npm run design:check # код против DESIGN.md
```

`src/api/http.ts` — реализация того же интерфейса поверх `fetch`. Адреса
и методы сверены с документом тестом, **но живого сервера этот клиент
не видел ни разу**: формы тел, коды состояния и заголовки проверятся
на первой стыковке.

## 7. Что удалить после эксперимента

Оболочка помечена в коде: `grep -rn "PROBE:" src` — 38 меток. Это тестовый
код OTP `1234`, демонстрационные карточки и заявки, панель пробы на лендинге,
список мебельщиков с вымышленными номерами.

Два места переживают эксперимент и переезжают дальше: `src/questions`
(формулировки вопросов и наборы вариантов) и `src/contract` (описание
того, чем обмениваются стороны).
