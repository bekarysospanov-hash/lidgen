# Контракт API lidgen

**Дата:** 15.09.2026
**Основано на:** `docs/prd-lidgen.md` §7 (истории и требования) · `docs/experiment-spec.md`
(§3 главное расхождение с ТЗ, §5 контур мебельщика, §8 ПДн) · `docs/story-map.md`
(срезы) · архитектурное решение `architect` (Fable), этап 2, 15.09.2026
**Для кого:** разработчик бэкенда — реализует сервер по этому документу.
На фронте контракт живёт в `src/contract` (zod-схемы), здесь — то же самое
прозой и таблицами, до кода
**Статус:** намерение, зафиксированное до реализации сервера. Фронт работает
на моках (`src/api/mocks`), которые обязаны реализовывать ровно этот контракт —
см. `CLAUDE.md`, конвенция «моки реализуют контракт, а не обходят его»

## 1. Назначение и правила

Документ описывает то, чем обмениваются фронт и сервер, — до того, как сервер
написан. Правила, которые держат стык:

- **Контракт меняется первым.** Понадобилось новое поле — правится
  `src/contract` и этот документ, потом мок, потом экран (`CLAUDE.md`).
  Обратный порядок — источник потерянной недели на стыковке.
- **Моки реализуют контракт целиком**, включая ошибки и пустые состояния.
  Мок, отвечающий «как удобно экрану», а не так, как должен ответить сервер, —
  главный источник ложной уверенности перед стыковкой.
- **JSON — camelCase.** Ни на входе, ни на выходе snake_case не используется.
- **Время — ISO-8601 UTC на проводе**, отображение в таймзоне браузера —
  забота фронта, сервер таймзону клиента не знает и знать не обязан.
- **Идентификаторы непрозрачны.** Ни `id`, ни `number`, ни `token` фронт
  не парсит и не выводит из формата — формат может меняться на бэкенде
  без правки контракта, пока проходит регэксп/тип поля. Единственное
  исключение — мок обязан генерировать `number` в формате `ГГММ-NNN`
  для правдоподобия на скелете (§10), но это свойство мока, не контракта.
- **Схемы — zod 4**, типы выводятся из схем (`z.infer`), схема одна на обе
  стороны: ею же валидируются и поля формы, и ответы API (моковые и настоящие).

## 2. Сущности

### Request

Ядро контракта. Полная серверная запись; ниже — все поля, которые когда-либо
у заявки есть. `RequestForClient` (§5, `getRequestByToken`) — это проекция
без `id`, `phone` и служебных полей маршрутизации, не отдельная сущность.

| Поле | Тип | Обязательность | Nullable | Становится обязательным на |
|---|---|---|---|---|
| `id` | uuid | всегда | нет | — (срез 1, технический, не отдаётся клиенту) |
| `number` | RequestNumber, 4–12 симв. | всегда | нет | срез 1 |
| `token` | Token, `^[A-Za-z0-9_-]{22,64}$` | появляется после `confirmOtp` | до этого момента отсутствует, не «null» | срез 1 |
| `status` | RequestStatus | всегда | нет | срез 1 |
| `createdAt` | Iso | всегда | нет | срез 1 |
| `phoneConfirmedAt` | Iso \| null | всегда присутствует как поле | да, пока не подтверждён | срез 1 |
| `routedAt` | Iso \| null | всегда присутствует как поле | да, пока не маршрутизирована | срез 1 (US-14) |
| `completedManually` | boolean | всегда, default `false` | нет | срез 2 (US-09) — на срезе 1 всегда `false` |
| `details` | Details (дискриминированный по `category`) | всегда | нет | срез 1 (только `kitchen`), остальные категории — срез 2 |
| `mainSize` | MainSize | всегда | нет | срез 1 |
| `description` | string, 1..2000 | всегда | нет | срез 1 |
| `city` | City | всегда | нет | срез 1 |
| `district` | string | опционально | да | срез 2 (US-08, не блокирует отправку) |
| `deadline` | string, свободный текст | опционально | да | срез 2 (US-08, не блокирует отправку) |
| `finishLevel` | `basic\|medium\|premium` | опционально | да | срез 2 (US-08) |
| `phone` | Phone, `^\+7\d{10}$` | всегда | нет | срез 1 — **не покидает сервер и кабинет мебельщика после отправки КП**, из `RequestForClient` исключён |
| `consent` | `{policyVersion, acceptedAt}` | **обязателен** | нет | срез 2 (US-11) — заявка без согласия не создаётся: `VALIDATION_FAILED path=consent` |
| `source` | `{utmSource?, utmMedium?, utmCampaign?, utmContent?, referrer?}` | опционально | — | срез 2 (US-26) |
| `clientRequestId` | uuid | опционально, только на входе `createRequest` | — | срез 1 — ключ идемпотентности, не поле для чтения заявки обратно |

> `quotes` в эту таблицу не входит: КП — отдельная сущность (`Quote`), связанная
> через `requestId`. `RequestForClient` собирает их в массив на чтении,
> сервер не обязан хранить их физически внутри записи заявки.

### MainSize

Общее поле всех категорий — **не** поле `details`, лежит на заявке напрямую.
Дискриминант `known` определяет, какие поля дальше обязательны.

| Поле | Тип | Когда обязательно |
|---|---|---|
| `known` | boolean | всегда — дискриминант |
| `meters` | number, `>0`, `≤30`, до 2 знаков после запятой | только при `known: true` |

Ветка «пока не знаю» (`known: false`) — валидный, самостоятельный вариант,
не ошибка валидации (US-05a). Она же переводит заявку в `incomplete` (§4).

### City

| Поле | Тип | Когда обязательно |
|---|---|---|
| `code` | `almaty \| astana \| shymkent \| other` | всегда |
| `name` | string \| null | обязателен (не `null`), если `code: 'other'`; иначе `null` |

Список выбираемых городов — часть контракта (этот enum). **Покрытие** —
то, есть ли на приёме мебельщики в этом городе, — свойство серверных данных,
не контракта (§4, `out_of_coverage`). Мок держит покрытие в
`src/api/mocks/coverage.ts` = `{almaty, astana, shymkent}` как заглушку
серверного правила (§10).

### Details — по категориям

Дискриминированный union по полю `category` **внутри** `details`
(не путать с полем-дискриминантом статуса заявки).

| `category` | Дополнительные поля | Срез |
|---|---|---|
| `kitchen` | `shape: straight\|corner\|u-shape\|island\|null` · `appliances: yes\|no\|undecided\|null` | срез 1 (US-05a), картинки для `shape` — срез 2 (US-05b) |
| `wardrobe` | `doors: swing\|sliding\|none\|null` · `toCeiling: boolean\|null` | срез 2 (US-06), картинки для `doors` — там же |
| `bathroom` | нет полей — заглушка, наполняется в US-07 | срез 2 |
| `other` | нет полей — заглушка, наполняется в US-07 | срез 2 |

Добавление полей `wardrobe`/`bathroom`/`other` в будущих срезах не ломает уже
сохранённые заявки категории `kitchen` — union расширяется веткой, а не общей
формой (US-04, сценарий «Ответы категории хранятся, не ломая заявку»).

### Quote

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | uuid | всегда |
| `requestId` | uuid | всегда |
| `master` | `{id, name}` | всегда |
| `composition` | string — состав решения | всегда |
| `materials` | string — материалы человеческим языком | всегда |
| `price` | `{minKzt: int, maxKzt: int ≥ minKzt}` | всегда — **только вилка**, одиночное число не принимается (US-19a) |

### Master

Мебельщик, принимающий заявки. Заводится нами (A2, предзаполняем карточки),
самостоятельной регистрации в пробе нет — US-20 «правка своей карточки»
стоит в срезе 3.

| Поле | Тип | Обязательность | Nullable |
|---|---|---|---|
| `id` | uuid | всегда | нет |
| `name` | string, 1..200 — название мастерской | всегда | нет |
| `city` | City | всегда | нет |
| `phone` | Phone — по нему же вход в кабинет (US-17) | всегда | нет |
| `acceptingFrom` | Iso \| null — **«на приёме» с этого момента** | всегда присутствует как поле | да, пока не на приёме |
| `card` | MasterCard \| null — публичная карточка каталога (US-02) | всегда присутствует как поле | да, пока карточка не заполнена и согласие не получено |

**«На приёме» — это заполненный `acceptingFrom`, а не отдельный флаг.**
Булево поле отвечает «да», но не отвечает «с какого числа»; на разборе
эксперимента нужно именно второе — заявка, пришедшая до выхода мебельщика
на приём, ему не маршрутизировалась, и это надо уметь объяснить, а не
угадывать. Снятие с приёма обнуляет поле: история «был на приёме тогда-то»
живёт в событиях, не в записи.

**`covered(city)` считается по этому списку** (§4): город покрыт, если в нём
есть хотя бы один мебельщик с заполненным `acceptingFrom`. До US-14 покрытие
было константой в моке (§10) — теперь у него есть источник данных.

**`phone` мебельщика — не ПДн заказчицы, но ПДн.** Наружу он уходит только
в каталоге (US-02, публичное контактное лицо мастерской, согласие получено
при заведении карточки) и никогда — в проекциях заявки.

### MasterCard

Публичная карточка каталога (US-02). Появляется **только** после того, как
мастерская дала согласие на публикацию и карточку заполнили мы (трек A2).

| Поле | Тип | Смысл |
|---|---|---|
| `about` | string, 1..600 | чем занимается, человеческим языком |
| `yearsOnMarket` | int ≥0 | сколько лет на рынке |
| `does` | string[], 1..6 | что умеет: «кухни», «шкафы-купе», «детские» |
| `photos` | url[], 1..6 | **свои работы**, снятые у заказчиков этой мастерской |
| `publishedAt` | Iso | когда согласие получено и карточка опубликована |

**Запрет, вынесенный из PRD в контракт, потому что нарушить его проще всего
здесь.** Сгенерированные карточки, спарсенные чужие портфолио и вымышленные
мастерские «для объёма» недопустимы. Причина измерительная: заявка, пришедшая
на несуществующее предложение, делает CPL неинтерпретируемым. Плюс чужие
фотографии — объект авторского права, а Asia Mebel известна именно в среде
мебельщиков, и узнают их работы мгновенно.

**Цен в карточке нет** ни в каком виде: на первом такте вместо цены —
что мастерская умеет (US-02).

**Пустой каталог — законное состояние.** Пока согласий нет, операция
возвращает пустой список, а каталог и блок на лендинге не показываются
вовсе: пустая сетка и карточки-заглушки запрещены тем же правилом.

### MasterProfile

Проекция `Master` для самого мебельщика: `{ id, name, city }`. Телефон свой
он и так знает, `acceptingFrom` — наше служебное состояние, не его.
Отдаётся один раз в ответе `masterConfirmCode` (§5) и живёт в памяти вкладки.

### Routing

Кому какая заявка ушла. Серверная запись, целиком не отдаётся никому:
заказчице из неё виден только факт (`routedAt` в §2), мебельщику — только
то, что заявка есть в его списке.

| Поле | Тип | Смысл |
|---|---|---|
| `requestId` | uuid | какая заявка |
| `masterIds` | uuid[], 1..3 | кому ушла — **до трёх** (US-14) |
| `routedAt` | Iso | когда ушла; то же значение кладётся в `Request.routedAt` |

**Правило рассылки (US-14).** Маршрутизируются **только `qualified`** (§4) —
ни `incomplete`, ни `out_of_coverage`. Получатели: мебельщики на приёме
в городе заявки, **не больше трёх**. Меньше трёх — рассылается скольким есть;
ноль невозможен по построению: город без единого мебельщика на приёме
не покрыт, и такая заявка получила бы `out_of_coverage` ещё в `confirmOtp`.

Чем три отобраны из большего числа — **правило владельца, не контракта**.
В пробе это порядок списка (§10, PROBE); на проде тут будет очередь,
рейтинг или ручной отбор дежурным, и контракт заранее не решает, какой.

**Переназначения нет.** Маршрут пишется один раз; «переслать другому,
раз эти молчат» — операция оператора, в срезе 1 её нет.

### Уведомление мебельщику (US-15)

Отправка сообщения в мессенджер — **серверная работа, у неё нет операции
в этом контракте**: фронт ничего не шлёт и ничего про канал не знает.
Единственный след, видимый фронту, — `routedAt` у заявки и событие `routed`
(§2, Event). Канал (WhatsApp / Telegram / оба) — открытый вопрос
`CLAUDE.md`, и он не влияет на форму данных.

### Event

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | uuid | всегда |
| `type` | EventType | всегда |
| `at` | Iso | всегда |
| `requestId` | uuid \| null | `null` для событий без привязки к заявке: `visit` и вход мебельщика в кабинет (`otp_requested`/`otp_confirmed` с `actor.role: master`, US-17) |
| `actor` | `{role: client\|master\|operator\|system, id?}` | всегда |
| `sessionId` | string | опционально — обязателен для событий воронки до отправки (US-25a) |
| `payload` | объект, форма зависит от `type` | опционально |

`EventType`: `visit · continue_clicked · category_selected · required_filled ·
request_submitted · otp_requested · otp_confirmed · routed · master_opened ·
quote_sent · client_page_opened · contact_made · manual_completion ·
request_closed`.

## 3. Идентификаторы

Три идентификатора заявки — ниже; четвёртый, `masterToken`, появился
вместе с кабинетом (US-17) и описан после таблицы.

| | `id` | `number` | `token` |
|---|---|---|---|
| **Формат** | uuid | строка 4–12 симв., только цифры и дефис | `^[A-Za-z0-9_-]{22,64}$`, ≥128 бит энтропии |
| **Кто видит** | сервер и кабинет мебельщика (URL `/master/requests/:id`) | обе стороны при дозвоне — диктуется по телефону | только заказчица, получившая его при подтверждении номера |
| **Срок жизни** | пока существует запись | пока существует запись | пока живут данные заявки (удаление US-28, ≤90 дней); TTL контрактом не задан |
| **Выдаётся** | при создании записи | при создании записи (мок: `createRequest` сразу генерирует `ГГММ-NNN`) | **только** в ответе `confirmOtp`, не при создании |

**Почему нельзя смешивать.**

- `id` привязан к модели доступа кабинета мебельщика (роль + сессия,
  `US-17`) — это защита по ролям, а не по владению секретом. Отдавать `id`
  на клиентскую страницу означало бы протащить в возможность доступа по
  предъявлению значения, за которым не стоит проверка роли.
- `token` — ровно наоборот: доступ даёт **владение строкой**, без роли и без
  пароля (US-21, «доступ получает тот, кто доказал владение номером»
  на входе, дальше — кто угодно, кому строку переслали, сознательно,
  см. допущение US-21). Подставить туда `id` или `number` вместо `token`
  превратило бы непубличный технический идентификатор или диктуемый по
  телефону код в секрет доступа — а они для секрета не годятся: `id` виден
  бэкенду и мебельщику по определению, `number` **намеренно короткий
  и произносимый**, то есть в мок-формате `ГГММ-NNN` перебираем за секунды.
- `number` — не credential вообще: он не проверяется никаким эндпоинтом
  как ключ доступа, это диктуемая по телефону метка для устного
  сопоставления заявки дежурным и мебельщиком. Ни один эндпоинт контракта
  не принимает `number` там, где ждёт `id` или `token`.

**Четвёртый — `masterToken`, сессия кабинета мебельщика (US-17).**

| | |
|---|---|
| **Формат** | `^[A-Za-z0-9_-]{22,64}$`, ≥128 бит энтропии — тот же `Token` |
| **Кто видит** | только вошедший мебельщик |
| **Срок жизни** | **12 часов** с выдачи, дальше вход заново |
| **Выдаётся** | только в ответе `masterConfirmCode` |

Совпадение формата с клиентским `token` — не повод их смешивать: **это
разные пространства**, и сервер не проверяет один там, где ждёт другой.
Клиентский `token` открывает **одну** заявку тому, кто им владеет; `masterToken`
открывает **список чужих заявок и право отправить КП** — цена ошибки разная,
поэтому и срок жизни разный: заявка живёт до 90 дней, сессия кабинета — до конца
рабочего дня.

Проверяется `masterToken` заголовком `Authorization: Bearer <masterToken>`,
а не полем в пути или теле: в URL он попал бы в логи прокси и в `Referer`,
а список заявок с чужими телефонами — не то, что стоит оставлять в чужих логах.

## 4. Статусная машина

Отдельного статуса «подтверждена» нет: подтверждение — это `phoneConfirmedAt`,
а `status` сразу содержательный, классифицируется синхронно внутри `confirmOtp`.

| Статус | Смысл | Кто переводит | Соответствует US-27 |
|---|---|---|---|
| `unconfirmed` | заявка создана, OTP не введён | `createRequest` (авто) | новая |
| `qualified` | телефон подтверждён, город в покрытии, `mainSize.known: true` — либо это стало так после дозвона | `confirmOtp` (авто) / оператор (US-09, дозвон) | квалифицированная |
| `incomplete` | телефон подтверждён, город в покрытии, `mainSize.known: false` | `confirmOtp` (авто) | неполная |
| `out_of_coverage` | телефон подтверждён, город **вне** покрытия — приоритетнее `incomplete` | `confirmOtp` (авто) | вне покрытия |
| `unreached` | была `incomplete` дольше 24 часов без дозвона | таймер (сервер, US-09) | недозвон |
| `routed` | `qualified`, заявка отправлена мебельщикам, `routedAt` заполнен | сервер (US-14) | маршрутизирована |
| `quoted` | по `routed`-заявке пришло первое КП | сервер, на приём `createQuote` (US-19a) | есть КП |
| `closed` | заявка закрыта из любого состояния | оператор | закрыта |

**Правило классификации внутри `confirmOtp`:**
`!covered(city) → out_of_coverage`; иначе `!mainSize.known → incomplete`;
иначе `qualified`. **`covered(city)` с US-14 перестала быть константой:**
город покрыт, если в нём есть хотя бы один `Master` с заполненным
`acceptingFrom` (§2). Свойством серверных данных, а не контракта, покрытие
при этом быть не перестало — изменился только источник данных. `out_of_coverage` приоритетнее `incomplete` — решение PM:
звонить туда, где некому передать заказ, — работа впустую; сырые данные
при этом сохраняются, заявка не теряется.

**Переходы:**

```
unconfirmed --confirmOtp--> qualified | incomplete | out_of_coverage      (фронт)
unconfirmed (код не введён)                          --> остаётся unconfirmed
                                                          = отвал US-12, считается отдельно

incomplete  --дозвон, внесён размер-->    qualified [completedManually=true, несъёмный]   (оператор)
incomplete  --24ч без дозвона-->          unreached                                        (таймер, US-09)

qualified   --маршрутизация-->            routed [routedAt]           (сервер, US-14;
                                                                        ТОЛЬКО qualified —
                                                                        ни incomplete, ни out_of_coverage)
routed      --первое КП-->                quoted                       (US-19a)

out_of_coverage --появилось покрытие-->   qualified                    (оператор, опционально)

любое статус --закрытие-->                closed                       (оператор)
```

**Когда происходит `routed`.** На проде маршрутизация — отдельный серверный
шаг после классификации: очередь, отбор получателей, отправка уведомлений
(US-15), и между `qualified` и `routed` проходит время. **В пробе сервера нет,
и мок маршрутизирует синхронно внутри `confirmOtp`** — заявка, ставшая
`qualified`, тем же вызовом получает `routedAt` и попадает в списки
мебельщиков (§10, PROBE). Для фронта разница невидима: он читает `status`
и `routedAt`, а не догадывается о них по времени ответа. **Контракт
синхронности не требует** — бэкенд вправе разнести эти шаги, и статус
`qualified` без `routedAt` остаётся законным состоянием.

**Первое КП переводит `routed → quoted`**, второе и третье статус не двигают:
`quoted` означает «есть хотя бы одно КП», а не «пришли все» (§5, `createQuote`).

**Фронт в срезе 1 делает только два перехода: создание (`unconfirmed`)
и подтверждение (`confirmOtp` → `qualified/incomplete/out_of_coverage`).**
Остальные переходы (`routed`, `quoted`, `unreached`, дозвон, `closed`) —
серверные или инициируются из кабинета мебельщика/оператором, не с публичной
формы. Это не значит, что они не нужны в срезе 1 по историям (`US-14`, `US-19a`
входят в срез 1 «Скелет» по `story-map.md`) — значит только то, что триггер
не на стороне заказчицы.

> ⚠️ **Расхождение, зафиксированное, а не тихо сглаженное.** Сценарий
> «Статус заявки — из одного списка» в `prd-lidgen.md` §7 (US-27) перечисляет
> семь имён: *новая · неполная · недозвон · квалифицированная ·
> маршрутизирована · есть КП · закрыта* — без «вне покрытия». Контракт
> заводит восьмое значение, `out_of_coverage`, потому что без него правило
> приоритета из §4 спеки эксперимента («звонить туда, где некому передать
> заказ, — работа впустую») нечем закодировать. Разработчику принимать это
> как восьмое состояние; PRD и таблицу наблюдения (US-27) стоит поправить
> отдельно, вне этого документа.

## 5. Тринадцать операций

Все операции: **восемь публичных**, которыми пользуется заказчица (шесть
скелета плюс приём событий воронки, US-25a), и **пять в кабинете мебельщика** — они ниже, отдельным блоком,
и все требуют `masterToken` (§3). Остальное — §9.

### `createRequest`

| | |
|---|---|
| HTTP | `POST /api/requests` |
| Тело запроса | `CreateRequest` (таблица ниже) |
| Тело ответа | `RequestCreated` |
| Успех | `201` |
| Ошибки | `VALIDATION_FAILED`, `RATE_LIMITED`, `INTERNAL` |
| События | `request_submitted` **и** `otp_requested` — оба, одним вызовом |
| Идемпотентность | да, по `clientRequestId` |
| Лимит | **per-phone**, не только per-IP — см. ниже |

**Лимит на `createRequest` считается по номеру телефона.** Каждая новая заявка
отправляет SMS за счёт проекта, а номер в теле запроса — чужой: его подставляет
тот, кто шлёт запрос. Без ограничения по `phone` любой желающий засыпает
сообщениями произвольного человека и выжигает бюджет на SMS, меняя IP или
`clientRequestId` между вызовами. Требование к боевому бэкенду: на один номер —
не больше **3 заявок в час** и **10 в сутки**, сверх лимита `RATE_LIMITED`
с `retryAfterSec`. Лимит по IP лимит по номеру не заменяет и наоборот:
первый защищает сервер, второй — владельца номера. В пробе лимит
не реализован (§6, резерв).

**Согласие на обработку ПДн обязательно на сервере, а не только на экране**
(US-11). Заявка без `consent` не создаётся: `VALIDATION_FAILED` с `path: consent`.
Проверка на экране — удобство, проверка на сервере — законность: форму можно
обойти инструментами разработчика, схему нельзя. Сервер сохраняет **версию
текста политики и время отметки**, а не булев флаг: доказывать придётся, с чем
именно человек согласился и когда, а текст политики со временем меняется.

**`CreateRequest`:**

| Поле | Тип | Обязательность |
|---|---|---|
| `details` | Details | обязательно |
| `mainSize` | MainSize | обязательно |
| `description` | string, 1..2000 | обязательно |
| `city` | City | обязательно |
| `phone` | Phone | обязательно |
| `district` | string \| null | опционально |
| `deadline` | string \| null, свободный текст | опционально |
| `finishLevel` | `basic\|medium\|premium\|null` | опционально |
| `consent` | `{policyVersion, acceptedAt}` | **обязательно** (US-11) |
| `source` | `{utmSource?, utmMedium?, utmCampaign?, utmContent?, referrer?}` | опционально |
| `clientRequestId` | uuid | опционально — см. ниже |

**`RequestCreated`:** `{ id, number, status: 'unconfirmed', createdAt, otp: OtpSent }`.

**`OtpSent`:** `{ channel: sms|whatsapp|telegram, codeLength: 4..6, retryAfterSec: int ≥0 }`.

**`clientRequestId` и идемпотентность.** Фронт генерирует его один раз на
попытку отправки формы (не при каждом клике) и переиспользует при ретрае —
сетевой таймаут, двойной клик, автоповтор клиента. Если заявка с таким
`clientRequestId` уже существует, сервер возвращает **ту же** `RequestCreated`
(тот же `id`, `number`, `otp`), не создаёт вторую запись и не отправляет
второй OTP. Единственное поле, которое при этом пересчитывается, —
`otp.retryAfterSec`: это «сколько осталось ждать **на момент ответа**», а не
слепок первого ответа. Кулдаун реально тает, пока идёт время, и вернуть
исходное число значило бы заставить фронт ждать дважды. `channel`
и `codeLength` при повторе те же. Отправка нового OTP при уже существующей заявке — это отдельная
операция, `resendOtp`, не повтор `createRequest`.

### `resendOtp`

| | |
|---|---|
| HTTP | `POST /api/requests/{id}/otp/resend` |
| Вход | `ResendOtpInput = { requestId }` — `requestId` приходит из `{id}` пути, тело запроса пустое; поле в схеме описывает логический вход операции для `src/contract` и `api/client.ts`, не форму тела на проводе |
| Тело ответа | `OtpSent` |
| Успех | `200` |
| Ошибки | `REQUEST_NOT_FOUND`, `ALREADY_CONFIRMED`, `OTP_RESEND_TOO_SOON`, `RATE_LIMITED` |
| События | `otp_requested` (тот же тип, что при создании — различать по `at` и, при необходимости, `payload`) |
| Идемпотентность | нет содержательного «повтора» — каждый вызов либо высылает новый код, либо отклоняется кулдауном |

Отдельной операции «запросить код» без `resendOtp` не существует: OTP уходит
автоматически при `createRequest`, `resendOtp` — единственный способ получить
код повторно.

### `confirmOtp`

| | |
|---|---|
| HTTP | `POST /api/requests/{id}/otp/confirm` |
| Вход | `ConfirmOtpInput = { requestId, code }` — `requestId` из `{id}` пути, тело запроса — `{ code: OtpCode }` |
| Тело ответа | `RequestConfirmed = { request: RequestForClient, token }` |
| Успех | `200` |
| Ошибки | `REQUEST_NOT_FOUND`, `OTP_INVALID`, `OTP_EXPIRED`, `OTP_ATTEMPTS_EXCEEDED`, `ALREADY_CONFIRMED`, `RATE_LIMITED` |
| События | `otp_confirmed` |
| Идемпотентность | да, **для верного кода**: повтор на уже подтверждённой заявке возвращает тот же `{request, token}`, без повторной классификации статуса. Неверный код на уже подтверждённой заявке → `ALREADY_CONFIRMED`, не `OTP_INVALID` |

Сервер синхронно классифицирует статус (§4) и выдаёт `token` в этом же ответе —
второго запроса за токеном нет.

**Требование к боевому бэкенду: идемпотентность `confirmOtp` ограничена
по времени и по числу попыток.** Как написано выше, операция бессрочно
отдаёт `token` по верному коду — а код четырёхзначный, `requestId` виден
кабинету мебельщика (§3), и подтверждённая заявка живёт до 90 дней. Без
ограничений это вечный оракул: 10⁴ вариантов перебираются за минуты,
и на выходе — доступ к чужой заявке.

- **Счётчик попыток работает и после подтверждения**, а не только до него.
  Лимит §6 ниже (5 попыток) считается на заявку, а не на «неподтверждённую
  заявку»; исчерпан — `OTP_ATTEMPTS_EXCEEDED` независимо от статуса.
- **Повторная выдача токена ограничена окном** — не больше **10 минут**
  с момента первого успешного `confirmOtp`. Этого хватает на ретрай из §8
  (ответ не дошёл, фронт повторяет тот же запрос через секунды) и совершенно
  не хватает на перебор. За пределами окна верный код отвечает
  `ALREADY_CONFIRMED`, а не токеном.
- **Сверх лимита — `RATE_LIMITED`** с `retryAfterSec`, считается по `requestId`
  и по источнику запроса.

В пробе ничего из этого не реализовано: код константа `1234`, лимитов нет
(§6, резерв; §10). Требование адресовано серверу, не моку.

### `uploadPhoto`

| | |
|---|---|
| HTTP | `POST /api/photos` |
| Тело | `multipart/form-data`, поле `file`, **один файл за вызов** |
| Ответ | `Photo` — `{ id, url, name, bytes, mime }` |
| Ошибки | `VALIDATION_FAILED` (`path: photo.mime` или `photo.bytes`), `RATE_LIMITED`, `INTERNAL` |

US-10. Ограничения, которые сервер обязан проверять сам, не полагаясь на фронт:

| Что | Значение | Почему так |
|---|---|---|
| Максимум файлов на заявку | **5** | шестой снимок не добавляет мебельщику знания, а вес заявки растёт |
| Максимум на файл | **10 МБ** | снимок с телефона помещается, видео и сканы отсекаются |
| Типы | `image/jpeg`, `image/png`, `image/webp`, `image/heic` | heic обязателен: так снимает iPhone по умолчанию |

`Content-Type` клиент **не выставляет** — его вместе с `boundary` ставит браузер;
заданный руками рвёт разбор на сервере.

**Загрузка не блокирует отправку заявки.** Снимки прикладываются к
`createRequest` полем `photos` (пустой список законен). Если загрузка не
удалась или человек её пропустил, заявка уходит без фото — требование US-10
«просим настойчиво, но не держим».

**`url` фронт не разбирает.** Реальный бэкенд отдаёт адрес хранилища, мок —
`blob:` вкладки; обе формы проходят одну схему. Это то же правило, что для
номера заявки (§1).

### `deletePhoto`

| | |
|---|---|
| HTTP | `DELETE /api/photos/{id}` |
| Тело | нет |
| Ответ | `204`, тело пустое |
| Ошибки | `INTERNAL`. Удаление несуществующего снимка **успешно**: повторное нажатие не должно падать |

Снятый до отправки снимок обязан исчезать и на сервере. Без этой операции

мусор: сервер подчистит его сборкой по времени жизни.

### `sendEvents`

| | |
|---|---|
| HTTP | `POST /api/events` |
| Тело запроса | `{ events: EventInput[] }` — пачкой, 1..50 за вызов |
| Ответ | `202`, тело пустое |
| Ошибки | `VALIDATION_FAILED`, `RATE_LIMITED`, `INTERNAL` |
| Идемпотентность | нет: повтор пачки создаёт вторые записи, дедуп — забота отправителя |

`EventInput` — это `Event` (§2) **без `id` и без `at`**: оба ставит сервер.
Время клиента доверия не заслуживает — часы на телефоне сбиты чаще, чем
кажется, и воронка по ним раскладывается неправильно.

`requestId`, и без `sessionId` их не с чем связать — воронка «зашёл →
начал → дошёл до отправки» рассыпается на несвязанные счётчики.

**Отказ приёма событий не должен ломать экран.** Аналитика — наблюдение,
а не работа продукта: не дошло — считаем по остальным источникам. Фронт
глотает ошибку этой операции молча, единственный из всех.

**Порядок доставки не гарантируется**, и сервер на него не опирается:
последовательность восстанавливается по `at`, который он же и проставил.

## 5б. Кабинет мебельщика

Пять операций US-17, US-18, US-19a. Все, кроме входа, требуют заголовок
`Authorization: Bearer <masterToken>` (§3); без него или с протухшим —
`MASTER_UNAUTHORIZED`, и фронт отправляет на экран входа.

### `masterRequestCode`

| | |
|---|---|
| HTTP | `POST /api/master/otp/request` |
| Тело запроса | `{ phone: Phone }` |
| Тело ответа | `OtpSent` — та же схема, что у заявки |
| Успех | `200` |
| Ошибки | `VALIDATION_FAILED`, `MASTER_NOT_FOUND`, `OTP_RESEND_TOO_SOON`, `RATE_LIMITED` |
| События | `otp_requested` с `actor.role: master` |
| Идемпотентность | нет — каждый вызов либо шлёт код, либо отклоняется кулдауном |

Вход по номеру и коду, пароля нет вовсе (US-17): мебельщик отвечает
на заявки с телефона между цехом и замерами, и пароль он забудет или запишет
на коробке. Тот же механизм, что у заказчицы, — но **своя пара операций,
а не переиспользование `resendOtp`**: тот привязан к `requestId` и без заявки
не существует.

**`MASTER_NOT_FOUND` раскрывает, есть ли номер в списке, — и в пробе это
осознанно.** Мебельщиков семь, они заведены нами и знают об этом; ответ
«вашего номера нет» экономит Марату десять минут на догадки, почему код
не приходит. **На проде так нельзя** — это перечисление пользователей по
номеру: сервер обязан отвечать одинаково, существует номер или нет, а «код
не пришёл» разбирать поддержкой. Записано здесь, чтобы разработчик бэкенда
не унаследовал пробное поведение молча.

### `masterConfirmCode`

| | |
|---|---|
| HTTP | `POST /api/master/otp/confirm` |
| Тело запроса | `{ phone: Phone, code: OtpCode }` |
| Тело ответа | `MasterSession = { master: MasterProfile, token: Token }` |
| Успех | `200` |
| Ошибки | `VALIDATION_FAILED`, `MASTER_NOT_FOUND`, `OTP_INVALID`, `OTP_EXPIRED`, `OTP_ATTEMPTS_EXCEEDED`, `RATE_LIMITED` |
| События | `otp_confirmed` с `actor.role: master` |
| Идемпотентность | нет: каждый успешный вызов выдаёт **новую** сессию, старая продолжает жить до своего срока |

`token` здесь — `masterToken` (§3), живёт 12 часов. Политика кода —
та же, что для заявки (§6, «Политика OTP»), включая лимит попыток и TTL;
отдельных чисел для кабинета контракт не заводит.

**Подтверждается только код, который сервер сам выслал на этот номер.**
Без этого требования лимит отправок не защищает ничего: код подбирается
в обход отправки вовсе, а `masterRequestCode` с его кулдауном оказывается
формальностью, которую можно не вызывать. Кода не выдавали, он просрочен
или уже использован — ответ `OTP_INVALID`, тот же, что на неверные цифры:
существование выданного кода вызывающему знать незачем.

`ALREADY_CONFIRMED` в этой операции **не бывает**: подтверждать нечего,
у сессии нет состояния «уже подтверждена» — есть только «выдана».

### `listRequestsForMaster`

| | |
|---|---|
| HTTP | `GET /api/master/requests` |
| Вход | только заголовок авторизации |
| Тело ответа | `RequestForMasterListItem[]` — **маршрутизированные этому мебельщику**, новые первыми |
| Успех | `200` |
| Ошибки | `MASTER_UNAUTHORIZED`, `RATE_LIMITED` |
| События | нет — открытие списка не событие воронки |
| Идемпотентность | чтение |

**Пустой список — законное состояние, а не ошибка.** На скелете он будет
пустым чаще, чем полным: заявок ещё нет. Экран обязан показывать пустоту
осмысленно, `404` здесь не возвращается никогда.

**Сортировка — часть контракта**, а не вкус экрана: `routedAt` по убыванию.
Мебельщик заходит посмотреть, что нового, и «новое» обязано быть сверху
у всех реализаций одинаково.

### `getRequestForMaster`

| | |
|---|---|
| HTTP | `GET /api/master/requests/{id}` |
| Вход | `id` заявки из пути + заголовок авторизации |
| Тело ответа | `RequestForMaster` |
| Успех | `200` |
| Ошибки | `MASTER_UNAUTHORIZED`, `NOT_ROUTED_TO_YOU`, `RATE_LIMITED` |
| События | `master_opened` |
| Идемпотентность | чтение |

**`REQUEST_NOT_FOUND` эта операция не возвращает никогда.** Несуществующая
заявка и чужая заявка отвечают **одинаково** — `NOT_ROUTED_TO_YOU`. Иначе
`id` перебирается на существование: кабинет отвечал бы «такой нет» на выдуманный
и «не ваша» на настоящий, а это уже утечка — сколько заявок в системе и какие
`id` живые. Разные ответы стоили бы удобства ровно ничего: Марату оба случая
одинаково означают «сюда мне нельзя».

### `createQuote`

| | |
|---|---|
| HTTP | `POST /api/master/requests/{id}/quote` |
| Тело запроса | `CreateQuote = { composition, materials, price: {minKzt, maxKzt}, leadTimeDays, photos? }` |
| Тело ответа | `Quote` (§2) — с проставленными `id`, `requestId`, `master`, `sentAt` |
| Успех | `201` |
| Ошибки | `VALIDATION_FAILED`, `MASTER_UNAUTHORIZED`, `NOT_ROUTED_TO_YOU`, `QUOTE_ALREADY_SENT`, `RATE_LIMITED` |
| События | `quote_sent` |
| Идемпотентность | **нет, и повтор запрещён явно**: второе КП по той же заявке от того же мебельщика — `QUOTE_ALREADY_SENT` |

`master` в ответе сервер проставляет **сам, из сессии**; в теле запроса его
нет и быть не может — иначе мебельщик отправляет КП от чужого имени.

**Вилка обязательна на сервере, не только в форме** (US-19a): `minKzt`
и `maxKzt` обязательны оба, `maxKzt ≥ minKzt`. Равенство границ схема
пропускает — это «твёрдая цена», законный ответ; чего она не пропускает,
так это отсутствия одной из границ. Нарушение → `VALIDATION_FAILED`
с `path: price.maxKzt`.

**Первое принятое КП переводит заявку `routed → quoted`** (§4) и делает
видимым `clientPhone` в проекции — **для этого мебельщика и только для него**
(§7). Второе КП по заявке статус не двигает.

**Правка КП — это US-19b, срез 3**, и её здесь нет: `updatedAt` в `Quote`
существует, но остаётся `null` — операции, которая его заполнит, контракт
пока не описывает. Ошибиться в вилке и не суметь поправить — известное
ограничение скелета, названное, а не забытое.

### Две проекции заявки для мебельщика

Разделены не ради экрана, а ради сервера: гонять описание и пять снимков
в списке из двадцати строк незачем. Обе **строгие** — лишнее поле роняет
разбор, а не проглатывается: так утечка телефона в список становится ошибкой
стыковки, а не тихой находкой на проде.

**`RequestForMasterListItem`** — решить «беру или нет»:

| Поле | Тип | Зачем |
|---|---|---|
| `id` | uuid | по нему открывается карточка, `/master/requests/:id` |
| `number` | RequestNumber | по нему говорят по телефону |
| `routedAt` | Iso | когда пришла **ему** — не когда создана |
| `category` | CategoryId | кухня или шкаф — брать ли вообще |
| `mainSize` | MainSize | 3.2 м либо «размер не назван» |
| `city` | City | поедет ли он туда |
| `district` | string \| null | тот же вопрос точнее |
| `deadline` | string \| null | успевает ли |
| `photosCount` | int ≥0 | **число, не снимки**: «есть 3 фото» |
| `quotedByMe` | boolean | отвечал уже или нет — иначе отвечает дважды |

**`RequestForMaster`** — назвать вилку:

| Поле | Тип | Зачем |
|---|---|---|
| `id`, `number`, `routedAt` | — | то же, что в списке |
| `details` | Details | целиком: форма кухни и техника считаются отдельно |
| `mainSize` | MainSize | главный размер |
| `description` | string | свободный текст заказчицы — **его он читает первым** |
| `city`, `district`, `deadline` | — | то же, что в списке |
| `finishLevel` | `basic\|medium\|premium` \| null | класс материалов — половина цены |
| `photos` | Photo[] | сами снимки (US-10) |
| `myQuote` | Quote \| null | своё отправленное КП: что он уже назвал |
| `clientPhone` | Phone \| null | **`null` до отправки своего КП, номер — после** |

**Чего в обеих проекциях нет никогда:** `token` заказчицы · `phone` до КП ·
`consent` · `source` (UTM) · `clientRequestId` · `status` · **чужие КП —
ни цен, ни имён мастерских**.

**Почему нет `status`.** Восемь состояний §4 — внутренняя кухня; мебельщику
из них полезен ровно один бит «я уже ответил», и это `quotedByMe`. Отдать
сырой статус значило бы объяснять на экране, чем `routed` отличается
от `quoted`, — работа без пользы.

**Почему нет чужих КП, даже счётчиком.** Ни цен, ни «ответили 2 из 3».
Счётчик выглядит безобидно, но давит на вилку: увидев, что двое уже ответили,
мебельщик ставит цену не от своей себестоимости, а от страха опоздать.
Эксперимент проверяет, назовёт ли он цену не выезжая, — подсказывать ему
ответ нельзя, иначе мы меряем свою подсказку.

**Имени заказчицы в проекции нет, потому что его нет в контракте вообще** —
форма имя не спрашивает. После отправки КП мебельщик получает номер и звонит
на «здравствуйте». Завести имя — правка формы заявки (US-08), отдельное
решение, не часть кабинета.

## 6. Ошибки

**Конверт:** `{ error: { code, message, ...поля кода } }`. `ApiErrorBody` —
дискриминированный union по `code`.

| Код | Доп. поля | HTTP (рекомендация) | В пробе |
|---|---|---|---|
| `VALIDATION_FAILED` | `fields: {path, message}[]` | `422` | эмитится |
| `REQUEST_NOT_FOUND` | — | `404` | эмитится |
| `OTP_INVALID` | — | `400` | эмитится |
| `OTP_EXPIRED` | — | `400` | **зарезервирован**, не эмитится |
| `OTP_ATTEMPTS_EXCEEDED` | `retryAfterSec` | `429` | **зарезервирован**, не эмитится |
| `OTP_RESEND_TOO_SOON` | `retryAfterSec` | `429` | эмитится |
| `ALREADY_CONFIRMED` | — | `409` | эмитится |
| `TOKEN_INVALID` | — | `404` | эмитится |
| `RATE_LIMITED` | `retryAfterSec` | `429` | **зарезервирован**, не эмитится |
| `INTERNAL` | — | `500` | **зарезервирован**, не эмитится |
| `MASTER_NOT_FOUND` | — | `404` | эмитится (US-17) |
| `MASTER_UNAUTHORIZED` | — | `401` | эмитится (US-17) |
| `NOT_ROUTED_TO_YOU` | — | `403` | эмитится (US-18) |
| `QUOTE_ALREADY_SENT` | — | `409` | эмитится (US-19a) |

**Четыре кода кабинета** (§5б) и что фронт делает по каждому:

| Код | Когда | Что делает экран |
|---|---|---|
| `MASTER_NOT_FOUND` | номера нет среди мебельщиков | «этого номера нет в списке» на входе; **на проде так отвечать нельзя**, см. §5б |
| `MASTER_UNAUTHORIZED` | нет `masterToken`, протух или отозван | уводит на вход, ничего не показывая |
| `NOT_ROUTED_TO_YOU` | заявка чужая **или** её не существует — ответ один | «эта заявка не ваша», назад к списку |
| `QUOTE_ALREADY_SENT` | второе КП по той же заявке | показывает уже отправленное КП вместо формы |

Клиент ключуется по `code`, HTTP-статус вторичен — фронт читает конверт,
не код ответа, чтобы смена статуса на бэкенде (400 ↔ 422, например) не ломала
обработку ошибок. Таблица выше — рекомендация бэку для логов и мониторинга,
не часть того, что проверяет фронт.

**Резерв:** четыре кода в пробе не наступают — `OTP_ATTEMPTS_EXCEEDED`,
`OTP_EXPIRED`, `RATE_LIMITED` и `INTERNAL`. Код всегда `1234` (§10), лимита
попыток нет, лимита частоты нет, мок держит состояние в памяти и падать ему
нечем. Решение PM: прод обязан уметь включить все четыре **не меняя
контракт** — коды уже в схеме `ApiErrorBody`, обработка на фронте написана
(`src/texts/request.ts`, `errorText`), бэкенду остаётся начать их эмитить.
Фронт обязан быть к ним готов и без мока, который их показывает: именно
поэтому они описаны здесь, а не «когда дойдут руки».

### Политика OTP — числа для боевого бэкенда

Контракт обязан назвать числа, иначе разработчик сервера вправе взять любые,
и «четыре цифры без лимита попыток» окажется формально соответствующим
документу. В пробе ничего из этого не действует (§10), требование адресовано
проду:

| Параметр | Значение | Почему так |
|---|---|---|
| Длина кода | **6 цифр** на проде (`OtpSent.codeLength`, схема допускает 4..6) | 10⁶ вместо 10⁴; фронт читает длину из ответа и подстраивается сам |
| TTL кода | **5 минут** с момента отправки | дальше — `OTP_EXPIRED`; дольше живущий код бессмысленно расширяет окно перебора |
| Лимит попыток ввода | **5 на заявку**, счётчик не сбрасывается новым кодом | исчерпан — `OTP_ATTEMPTS_EXCEEDED` с `retryAfterSec`; считается и после подтверждения (§5, `confirmOtp`) |
| Кулдаун `resendOtp` | **30 секунд** между отправками | `OTP_RESEND_TOO_SOON` с `retryAfterSec`; единственное из списка, что мок реально умеет |
| Лимит отправок кода | **5 на заявку** и **10 на номер в час** | иначе `resendOtp` превращается в SMS-пушку по чужому номеру за счёт проекта (§5, лимит `createRequest`) |
| Окно повторной выдачи токена | **10 минут** после первого подтверждения | ретрай из §8 укладывается; перебор — нет (§5, `confirmOtp`) |

Ни одно из этих чисел не меняет форму запросов и ответов: они описывают,
**когда** сервер обязан ответить уже описанным кодом ошибки.

**Клиентские коды — не часть wire-контракта**, существуют только в
`api/client.ts`:

| Код | Когда |
|---|---|
| `NETWORK` | запрос не дошёл или не вернулся (таймаут, обрыв, DNS) |
| `CONTRACT_VIOLATION` | ответ сервера пришёл, но не прошёл zod-валидацию по этому контракту — главный страж стыковки: падает громко, а не тихо подставляет `undefined` |

## 7. Безопасность и ПДн

- **Токен в URL без второго фактора** — принятый компромисс US-21. Доступ
  получает тот, кто доказал владение номером телефона один раз (прошёл OTP);
  дальше строка равна доступу. Осознанно: цикл мебели идёт с пересылкой
  ссылки мужу, который утверждает сумму (§3, US-21) — это не обход защиты,
  а расчётный сценарий.
- **Телефона нет в клиентской проекции.** `RequestForClient` не содержит
  `phone` ни в каком виде — ни целиком, ни маскированно.
- **Контакт заказчицы раскрывается мебельщику только после отправки КП.**
  Это требование ПДн, а не деталь экрана: до КП `clientPhone` в проекции
  равен `null` — телефон **не приходит на фронт скрытым**, не маскируется
  и не лежит в ответе под флагом. Скрыть на клиенте то, что сервер уже
  прислал, невозможно: значение видно в инструментах разработчика любому.
  Правило держится на сервере, иначе оно не правило.
  **Зачем именно так:** маршрутизация отдаёт одну заявку троим, а заказ
  получит один. Без этого условия семь мастерских получают поток чужих
  телефонов просто за факт присутствия на приёме — это уже не сведение
  заказчика с исполнителем, а раздача базы. Отправленное КП — минимальная
  плата за контакт: мебельщик назвал цену, значит заявку прочитал.
- **`localStorage` запрещён, `sessionStorage` — с одним названным
  исключением** (US-11, спека §8, `CLAUDE.md`). Ни телефон, ни черновик
  заявки, ни клиентский `token` не кладутся никуда.
  Исключение — **`masterToken` в `sessionStorage` кабинета**: мебельщик
  ходит между списком и формой КП и обновляет страницу, а вход по коду
  на каждый F5 означает, что кабинетом не пользуются. В хранилище уходит
  **только строка сессии**: ни телефона, ни имени, ни заявок — то есть
  ничего, что спека §8 называет персональными данными. Ограничения те же,
  что у `history.state`: вкладка закрыта — сессия потеряна; 12 часов (§3) —
  и она мертва независимо от хранилища. Заказчицы это исключение
  не касается вовсе.
- **Где токен всё-таки переживает перезагрузку: `window.history.state`.**
  Формулировка «в браузере не хранится ничего» была неточной, и точность
  здесь важнее красоты. После подтверждения фронт переходит на страницу
  «заявка принята», передавая `{number, token, status}` состоянием навигации
  (`navigate(..., { state })`); браузер держит это состояние в истории вкладки
  и возвращает его при F5. Значит:
  - `token` **переживает перезагрузку** в пределах той же вкладки и той же
    записи истории — и это ровно то, чего от страницы ждут: обновление
    не должно терять единственную ссылку на заявку;
  - `token` **не переживает** закрытие вкладки, переход по новому адресу
    и открытие ссылки на другом устройстве — история не синхронизируется
    и на диск как хранилище сайта не ложится;
  - **телефона в `history.state` нет** — и это главное. Проверяется грепом:
    в состояние кладутся только `number`, `token` и `status`.
  Практическое следствие для §8 ниже не меняется: если вкладка закрыта,
  восстанавливать `token` фронту неоткуда.
- **`id` не покидает сервер и кабинет мебельщика** (§3) — не появляется ни
  в одном ответе, адресованном заказчице.
- **`number` не является credential.** Ни один эндпоинт не принимает его
  как альтернативу `token` или `id` для доступа к данным заявки — это
  устная метка для дозвона, короткая и намеренно угадываемая в диалоге
  человек-человек, непригодная как секрет.
- **OTP без лимита — только в пробе.** См. §6, резерв `OTP_ATTEMPTS_EXCEEDED`
  и `OTP_EXPIRED`.
- **Локализация ПДн (закон РК)** — вопрос хостинга, не контракта; владелец
  решения PM, срок — до GATE 1 (`CLAUDE.md`). Контракт не задаёт, где физически
  лежат данные, только форму, в которой они передаются между фронтом и сервером.

## 8. Поведение при сбоях сети

**На отправке заявки.** Фронт хранит один сгенерированный `clientRequestId`
на попытку отправки формы (не пересоздаёт на каждый ретрай) и повторяет
`createRequest` с тем же значением при таймауте или обрыве. Сервер обязан
дедуплицировать по `clientRequestId`: второй и последующий вызов с тем же
значением возвращает уже созданную `RequestCreated` без создания второй
заявки и без второй отправки OTP (§5). Итог для пользователя — двойной клик
«Отправить» или потеря связи на секунду не плодит дублей, за которыми потом
придётся отдельно гоняться при подсчёте CPL (спека §7, «дубли по телефону
схлопываются» — этот механизм закрывает более частый случай раньше, на уровне
самой отправки, а не постфактум).

**На подтверждении кода.** `confirmOtp` идемпотентна для верного кода (§5):
если ответ не дошёл до фронта (сеть оборвалась после того, как сервер уже
обработал код), повторная отправка того же запроса с тем же кодом безопасна
и возвращает тот же `{request, token}` — новой классификации статуса не
происходит, второй `otp_confirmed` не по смыслу переклассификации, а по факту
идентичного запроса (реализация решает, писать ли повторное событие —
контракт этого не запрещает и не требует).

Если вкладка потеряна полностью — не ретрай того же запроса и не перезагрузка,
а новый заход (человек закрыл страницу, вернулся через час с другого
устройства) — восстановления через сам фронт нет: `token` не хранится
ни в `localStorage`, ни в `sessionStorage` (§7), а всё, что его переживало, —
состояние записи истории закрытой вкладки. `confirmOtp` же требует код,
который живёт в сообщении, а не в памяти страницы. Перезагрузка (F5) в той же
вкладке заявку не теряет — токен приходит обратно из `history.state` (§7). Рабочий фолбэк — **ссылка, присланная
в мессенджер после подтверждения** (US-16): она несёт `token` напрямую
в URL и не требует повторного ввода кода. До первого успешного `confirmOtp`
фолбэка нет и не должно быть — токен просто ещё не существует (§3, «выдаётся
только в ответе `confirmOtp`»); единственный путь — `resendOtp` и новая
попытка `confirmOtp` с новым кодом.

Не входит в текущие одиннадцать операций (§5, §5б) и текущие схемы;
перечислено, чтобы бэкенд-разработчик не проектировал эти куски вслепую,
когда до них дойдёт очередь по `story-map.md`.

| Что | История | Что понадобится |
|---|---|---|
| Повторная выдача ссылки по номеру | US-21 | `POST /api/client/link-resend { phone }` — не описан в текущих операциях, отдельная точка входа для «потерял ссылку» |

| Переназначение маршрута | US-14 | «эти молчат, отдать другим» — действие оператора, `Routing` пишется один раз (§2) |
| Источник (UTM) как срез отчётности | US-26 | `source` уже есть в `CreateRequest`, но нет операции чтения/агрегации по нему — измерение живёт вне API, в таблице наблюдения (US-27) |

## 10. Что делают моки и PROBE-части

Моки (`src/api/mocks`) реализуют контракт в памяти — включая ошибки и пустые
состояния (§1). Часть их поведения — оболочка пробы, помечается `// PROBE:`
и удаляется на утилизации (`grep -rn "PROBE:"`, не по памяти — `CLAUDE.md`):

| Часть | Где | Почему PROBE |
|---|---|---|
| Код `1234` всегда проходит | `src/api/mocks/otp.ts` | заменяет реальную отправку и проверку OTP; на проде код — не константа |
| Подсказка «тестовый код 1234» в текстах интерфейса | `src/texts` | существует только пока OTP не настоящий |
| Искусственная задержка ответа | моки целиком | имитирует сетевой RTT реального бэка для проверки UI-состояний загрузки |
| Мок-нумерация `ГГММ-NNN` | `src/api/mocks` (генератор `number`) | стенд-ин серверного правила нумерации; реальный формат бэкенд выбирает сам, фронт его не парсит (§1) |
| Мок-покрытие городов `{almaty, astana, shymkent}` | `src/api/mocks/coverage.ts` | **заменяется списком мебельщиков на приёме** (US-14): покрытие считается по `Master.acceptingFrom`, а не по константе |
| Код `1234` проходит и на входе мебельщика | `src/api/mocks` | то же, что у заявки: реальной отправки кода нет |
| Мок-список мебельщиков на приёме | `src/api/mocks` | на проде это данные, заведённые нами (A2), и их редактирование — US-20 |
| Выбор троих получателей по порядку списка | `src/api/mocks` | правило отбора — решение владельца (§2, Routing), а не контракта; на проде тут очередь, рейтинг или ручной отбор |
| Маршрутизация синхронно внутри `confirmOtp` | `src/api/mocks` | на проде это отдельный серверный шаг с уведомлениями (§4, US-15); контракт синхронности не требует |

## 11. Порядок изменения контракта

**Expand-contract**, не ломающие правки сразу: сначала схема в `src/contract`
и этот документ, потом мок, потом экран (`CLAUDE.md`). Порядок обратный
подразумевает, что экран уже поверил в форму данных, которой ещё нет
в контракте, — источник рассинхрона.

Ломающие изменения (переименование или удаление поля, смена типа,
несовместимое изменение формата идентификатора) **до стыковки с реальным
бэком запрещены без записи в журнал изменений ниже** — журнал существует,
чтобы разработчик бэкенда, подключаясь позже, видел не только финальное
состояние контракта, но и что в нём менялось и почему.
